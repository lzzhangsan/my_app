# 高效协作调试手册（全应用 · 证据优先）

> **用法**：把本文件发给 Cursor / 其他 AI / 协作者，并说明「按此手册协作」。  
> **适用范围**：本应用（`my_app`）上的**一切问题**——任意网站、任意功能、UI、下载、智能手势、媒体库、构建安装等。  
> **不是**：只针对某一个网站或某一种报错的专项说明。

---

## 1. 一句话原则

**用最短闭环把问题调到理想状态：先证据，后改码；以当前产品行为 + 当前仓库实现为准，少猜、少空转。**

别站 / 别功能的成功经验可以参考，但**不能凌驾于「当前场景的实际表现」和「当前代码真实路径」之上。**

---

## 2. 为什么这是最高效方式

| 低效 | 高效（本手册） |
|------|----------------|
| 凭经验或类比大改 | 一次真实复现 + 日志钉因果链再改 |
| 开子智能体空翻仓库 | 已可复现时直接读相关代码 + logcat |
| 同时改多条不确定路径 | 一次只修一条已证实因果链 |
| 改完靠猜「应该好了」 | 最小复测 + 用户一句结果闭环 |
| 失败时悄悄做错事 | fail-closed：明确失败，不产生错误副作用 |

目标不是「写得多」，而是**反馈周期最短、误修最少**。

---

## 3. 角色分工（全问题通用）

| 角色 | 负责 | 不负责 |
|------|------|--------|
| **用户** | 说清目标/现象；按步骤操作一次；回传一句结果 | 不必自己定位根因、不必贴无关长日志 |
| **助手** | 结合现状与代码；必要时加短前缀日志；拉/筛运行日志；据证据改码；给出最小复测 | 不靠长篇猜测交差；不为「可能」做大范围无效探索 |

---

## 4. 标准闭环（任何问题都走）

```
目标或现象 →（需要时）短前缀日志 → 清 logcat / 准备环境
          → 热重启或约定安装方式 → 用户操作一次
          → 助手筛日志 / 对照代码 → 因果链
          → 只改证据指向的那一层 → 最小复测 → 一句结果
          → 成功则进入下一目标；失败则带着新证据再走一圈
```

### 4.1 用户怎么描述（最少信息）

```
目标或现象：……
操作步骤：……
结果：成功 / 失败（失败时：看到什么、和预期差在哪）
```

有截图更好；没有也可以。**一句结果往往比长描述更有用。**

### 4.2 助手怎么交付

1. **结论**（1–3 句：证据说明什么）  
2. **改动**（改了哪条因果链、为什么）  
3. **复测**（通常：热重启 R → 按某步骤操作一次 → 回结果）  

不擅自 commit / push；不主动做破坏性重装或清数据。

---

## 5. 证据怎么取（按问题类型选，不绑死某一站）

优先用**能证明因果**的证据，而不是堆信息：

| 问题类型 | 优先证据 |
|----------|----------|
| 网页内行为 / 长按 / 注入 JS | 带统一前缀的 `debugPrint` + `adb logcat`（如 `FB_DL`、`SMART_*`、自定前缀） |
| 下载 / 媒体入库 / 查重 | 同上 + 关键阶段标签（收到消息 → 解析 → 下载 → 写库） |
| UI / 交互 / 手势 | 现象描述 + 必要时界面截图 + 相关状态日志 |
| 原生 / 权限 / 安装 | logcat、安装方式是否覆盖安装、是否误卸装 |
| 构建失败 | 完整编译错误片段，而不是「编不过」三个字 |
| 逻辑不确定 | 先读当前调用链；证据不足再**针对性**加日志，而不是先大重构 |

**原则**：日志要短前缀、分阶段；禁止漫天无结构的打印。

---

## 6. 本应用工程约束（协作时默认遵守）

这些是**全应用**效率与安全底线，与具体网站无关：

1. **热重启优先（R）** 验证 Dart / 注入 JS 改动。  
2. **原生 / Kotlin 等变更**才覆盖安装：`adb install -r`。  
3. **禁止**无 `-r` 的 `flutter install`（会卸载并清空用户数据）。  
4. 调试启动可参考：`tool/run_debug_phone.bat`（清代理、覆盖安装、attach 等以脚本实际为准）。  
5. 主逻辑大量在 `lib/`（如 `browser_page.dart` 等）；改前先对齐真实调用路径。  
6. **一次一条因果链**：例如先「下对媒体」，再「有声音」，再「智能连下稳定」——不要并行瞎改。  
7. **fail-closed**：宁可不完成并说清原因，也不要错误下载、假重复挡下载、清错数据等副作用。

---

## 7. 子智能体与探索的使用边界

| 适合 | 不适合 |
|------|--------|
| 完全陌生的大模块摸底 | 用户已能稳定复现的问题 |
| 需要并行查多处且本地无线索 | 已有日志前缀、只需对一次操作 |

**默认可复现问题：本地代码 + 手机日志闭环。** 不要为了「看起来在干活」而启动耗时子智能体。

---

## 8. 给其他 AI 的执行指令（照做即可）

当你读到本手册时，对**本应用后续所有问题**：

1. 采用 **证据优先闭环**，不要先写长方案空谈。  
2. 以 **当前场景实际表现 + 当前仓库代码** 为准；外部经验仅参考。  
3. 证据不足时：先补**短前缀、分阶段**日志，再让用户操作一次，再改码。  
4. 一次只修一条已证实因果链；修完给最小复测步骤。  
5. 遵守第 6 节工程约束（热重启、`adb install -r`、禁止误卸装、不擅自 commit/push）。  
6. 用户确认本目标成功后，再进入下一个目标。

---

## 9. 「理想状态」如何推进（通用）

不要一次追求「整个 App 完美」。按用户当前目标拆步：

1. 用户给出**当前最在意的理想状态**（一句话）  
2. 用闭环把它做到  
3. 勾选确认后，再问/再接下一个理想状态  

示例拆法（仅作结构示范，不限站点）：

- 当前页操作结果正确  
- 无错误提示 / 无错误副作用  
- 媒体质量达标（如需要含音频）  
- 自动化/智能流程在该场景稳定  
- 回归时有稳定日志前缀可秒对
