# 高效协作调试方式终版（全应用 · 证据驱动 · 双向日志）

> **适用范围**：`my_app` 的功能开发、缺陷修复、UI 调整、网页适配、下载与媒体入库、智能手势、构建安装和性能问题。  
> **使用方式**：在新对话中说明“请按 `docs/高效协作调试方式终版.md` 协作”。  
> **核心目标**：用最短、可验证、可回退的闭环，把当前目标做到理想状态，同时保护用户数据和已有代码。

---

## 1. 核心精神

**解决问题以证据为核心，不凭感觉、惯性经验或未经验证的猜测直接改代码。**

基本处理方式：

1. **已有证据**：直接读取并核对证据，沿真实调用链定位根因，修改证据指向的环节。
2. **证据不足**：先读相关代码，明确“需要证明什么”，再添加最小调试日志；复现一次、取得证据后再修改。
3. **修改完成**：使用相同观察点复测，证明问题确实解决，而不是只判断代码“看起来应该可以”。

经验的作用是提出排查方向和验证假设，不能代替证据成为改码依据。

执行原则是：**先明确预期，再理解对象和检查现状；证据足够就改，证据不足才补日志；改动保持最小，验证与风险相匹配。**

### 1.1 修改前先建立“对象运行模型”

在解决问题或调整代码前，必须先对问题涉及的对象建立一个**足够完整、由证据支撑的运行模型**，然后才能选择修改入口。这里的“对象”可能是某个网站、媒体格式、页面组件、下载协议、数据结构、插件、原生系统能力或跨层调用链。

至少要回答与本次问题直接相关的事项：

1. **对象结构**：它由哪些元素、数据、资源或模块组成，哪些只是界面表象，哪些才是真实数据源。
2. **生命周期**：它何时创建、更新、切换、销毁，以及异步任务在页面或状态变化后是否仍会继续。
3. **官方或主路径**：系统本身如何完成目标操作；能够复用官方语义入口时，优先复用，而不是从表面现象反向猜测。
4. **关键不变量**：哪些已有能力和用户体验绝不能被破坏，例如当前媒体身份、正常播放速度、登录状态、页面切换、下载完整性和用户数据安全。
5. **失败与回退路径**：每层失败如何被确认，何时重试、何时降级，以及如何避免卡死、误报成功和错误副作用。
6. **可观察点**：用哪些代码、日志、测试、网络响应、官方文档或可复现场景证明上述判断。

“全面透彻”不等于无限研究，也不要求把整个系统的所有细节都读完。它的完成标准是：**已经足以解释当前现象、识别正确入口、预见主要副作用并设计可验证的改动**。如果仍不能解释关键现象，就继续调查或补证据，不应直接扩大修改。

例如，网页里的 `blob:` 地址可能只是播放器表面的临时入口；真实媒体可能来自页面数据模型、Service Worker 分段流或网站自己的下载管理器。若没有先弄清这些层次，只围绕 `blob:` 反复修补，就可能暂时绕过一个症状，却引发下载不完整、媒体错位、播放异常或交互失效等回归。

因此，经验和外部资料的正确用途是帮助建立候选模型；最终模型仍必须由当前代码、实际运行证据、官方实现或可重复测试加以确认。

判断优先级如下：

1. 当前用户目标和实际表现
2. 当前仓库的真实实现与调用链
3. 运行日志、测试、截图、网络响应等直接证据
4. 框架文档和外部经验
5. 未经验证的猜测

外部经验可以帮助缩小范围，但不能覆盖当前场景的事实。

## 2. 双方分工

### 用户负责

- 说明当前最想实现的结果。
- 必要时在真实设备上完成一次最小操作。
- 用一句话反馈是否达到预期；失败时说明看到了什么。
- 对涉及产品取舍、数据清理、破坏性操作或范围扩张的事项作决定。

### 助手负责

- 主动检查工作区、代码、调用链和已有证据。
- 能自行完成的读取、筛选、构建、测试和日志分析，不转交给用户。
- 证据不足时只增加短前缀、分阶段、可清理的诊断信息。
- 根据证据实施最小、可回退的修改。
- 完成与风险相称的静态验证和运行验证。
- 清楚说明结论、改动、已验证内容和最小复测步骤。

用户不需要自行定位根因，也不需要粘贴大段无关日志。

## 3. 标准闭环

```text
明确目标和预期
→ 确定本次问题涉及的对象、边界和不可破坏的已有能力
→ 检查工作区、当前实现、真实调用链和已有证据
→ 建立足以解释现象的对象运行模型
→ 判断证据是否足够
   ├─ 足够：直接修正证据指向的环节
   └─ 不足：明确待证明事项，加入最小诊断信息，
             复现一次并建立因果链
→ 实施最小、可回退的改动
→ 完成静态检查 / 测试 / 构建
→ 按改动类型进行最小运行复测
→ 检查副作用和邻近场景
→ 成功则清理临时诊断信息并交付
→ 失败则保留新证据，进入下一轮短闭环
```

一次聚焦一条因果链，但可以读取这条链所经过的全部必要上下游。例如：

```text
手势触发 → Dart 回调 → JS 注入 → 页面返回消息
         → 资源解析 → 下载 → 查重 → 媒体入库
```

“一次一条因果链”限制的是修改范围，不是机械地只看一个文件。

---

## 4. 问题描述的最小格式

首次提出问题时，优先提供：

```text
目标或预期：我希望……
操作步骤：我做了……
实际结果：现在出现……
```

复测时通常只需回复：

```text
成功
```

或：

```text
失败：看到……
```

如问题与界面、时间顺序或特定内容有关，截图、录屏、页面地址、发生时间和示例内容会提高定位效率，但不是所有问题都必须提供。

---

## 5. 证据分级

优先使用最接近因果关系、获取成本最低的证据。

| 级别 | 证据 | 典型用途 |
|------|------|----------|
| A | 编译错误、测试失败、明确异常栈、确定性代码错误 | 可直接定位时无需额外复现 |
| B | 可稳定复现的现象、短前缀阶段日志、状态变化 | 建立运行时因果链 |
| C | 截图、录屏、网络响应、数据库或媒体库结果 | 验证 UI、数据和外部交互 |
| D | 框架文档、同类实现、历史经验 | 缩小范围或解释机制 |
| E | 猜测 | 只能生成验证动作，不能直接支持大改 |

证据不只等于 `logcat`。明显的静态错误、测试结果或错误状态本身已经足够时，不为了形式额外加日志。

## 6. 按问题类型选择证据

| 问题类型 | 优先证据 |
|----------|----------|
| 网页行为、长按、JS 注入 | 页面实际表现、统一前缀日志、消息收发阶段 |
| 下载、解析、查重、媒体入库 | 收到请求 → 解析资源 → 下载 → 写入 → 刷新各阶段结果 |
| UI、布局、动画、手势 | 截图或录屏、组件状态、必要的交互日志 |
| 原生 Android、权限、安装 | 原生异常栈、`logcat`、包与权限状态、安装方式 |
| 构建失败 | 第一处有效编译错误及其上下文 |
| 性能问题 | 可重复的时间点、耗时、帧率、资源占用或性能轨迹 |
| 数据错误 | 修改前后数据、查询条件、写入结果和副作用 |
| 逻辑不确定 | 先读真实调用链，再在关键分支补最小日志 |

日志规范：

- 使用短而唯一的前缀，如 `SMART_*`、`FB_DL` 或本轮专用前缀。
- 记录关键阶段、输入类别、分支选择和结果，不打印无关对象全集。
- 避免输出令牌、Cookie、账号信息和用户私密内容。
- 临时日志在问题闭环后删除；确有长期诊断价值的日志才保留。

### 6.1 双向可见的一键日志方式

项目提供：

```text
tool/debug_log.bat
tool/debug_log.ps1
```

这套工具让用户和助手查看同一份证据：

- 用户双击 `tool/debug_log.bat`，可以在窗口中实时查看日志。
- 助手可以直接读取工具保存在 `debug_logs/` 下的完整日志。
- 屏幕可以只显示指定前缀，但保存的文件始终包含该应用进程的完整原始日志，避免筛选时遗漏上下文。
- 工具只读取日志：不安装或卸载应用、不清除应用数据、不停止 Flutter 调试进程。
- 对会过滤 Flutter `logcat` 的 Vivo 等设备，调试版 App 会把 `print`、`debugPrint` 和未处理异常同步写入应用内调试文件；电脑工具优先通过 `adb run-as` 实时读取该文件，失败时才回退到 `logcat`。

#### 用户最简操作

先确认 App 已经在手机上运行，再双击：

```text
tool/debug_log.bat
```

然后：

1. 日志窗口会直接持续显示并保存全部 App 日志，不需要输入前缀。
2. 在手机上正常使用或复现问题。
3. 发现问题后先保留现场，不要立即刷新、重启或重新安装 App。
4. 可以保持日志窗口继续运行；需要结束本次采集时按 `Ctrl+C`。
5. 回复助手“操作完成”，并简述问题现象、操作步骤、预期结果和实际结果。

如果是在自由测试中首次发现问题，但当时没有打开日志工具，应先描述问题；然后按助手给出的步骤打开日志工具并针对该问题复现一次。

也可以在终端直接指定前缀：

```text
tool\debug_log.bat SMART_
tool\debug_log.bat FB_DL
```

指定前缀只会减少窗口中显示的行，保存到文件的仍是该 App 进程的完整日志。日常持续测试直接双击、不传前缀即可。

#### 日志文件

每次采集都会生成带时间戳的完整日志：

```text
debug_logs/20260729_184500_SMART_.log
```

并更新两个固定入口：

```text
debug_logs/debug_log_latest.log
debug_logs/debug_log_latest.path.txt
```

助手默认先读取 `debug_log_latest.log`，需要比对多轮操作时再读取时间戳文件。`debug_logs/` 已被 Git 忽略，因为运行日志可能包含页面地址或用户操作信息。

#### 默认清理与保留旧缓冲区

工具默认只清除 Android 的旧 `logcat` 缓冲区，让本轮证据不受历史输出干扰；这不会清除应用数据。若其他调试会话正在依赖旧缓冲区，可使用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tool\debug_log.ps1 -NoClear
```

#### 设备与应用要求

- 手机已连接并授权 USB 调试。
- App 已经启动；工具按启动时检测到的 App 进程 PID 采集日志。
- 只有一台设备时会自动选择；连接多台设备时由助手通过 `-DeviceId` 指定。
- ADB 不必预先加入 `PATH`，工具会检查项目当前使用的常见 Android SDK 位置。

若启动失败，窗口会明确说明是 ADB、设备授权、设备数量还是 App 未运行的问题。

#### 重启与日志窗口的关系

- **热重载或热重启**：App 进程通常不变，当前日志窗口一般可以继续使用。
- **覆盖安装、冷启动或桌面重启脚本**：App 进程 PID 会变化，旧日志采集随旧进程失效。新 App 启动后，应关闭旧日志窗口并重新双击 `tool/debug_log.bat`。
- **App 崩溃或被系统结束**：当前 PID 日志会停止。重新打开 App 后，也要重新启动日志工具。

日志窗口只负责显示和保存日志，不接收 Flutter 的热重载、热重启按键。

## 7. 修改前保护

每次改码前，助手默认执行以下检查：

1. 查看工作区状态，识别用户已有的修改和未跟踪文件。
2. 明确当前问题涉及的对象、边界、目标行为和不可破坏的已有功能。
3. 阅读与当前因果链直接相关的代码、配置和上下游实现，建立对象运行模型。
4. 对陌生、外部或持续变化的对象，必要时核对其官方文档、官方源码、协议或真实页面结构。
5. 确认准备修改的是根因所在的真实入口，而不是界面表象或偶然症状。
6. 不覆盖、不回退、不格式化无关的用户改动。
7. 不使用破坏性 Git 命令恢复工作区。
8. 不擅自 commit、push、开 PR 或清理文件。
9. 若当前修改会与用户已有改动冲突，先说明冲突和可选处理方式。

修改应尽量做到：

- 范围小；
- 原因明确；
- 容易审查；
- 容易回退；
- 不顺手重构无关代码。

如果根因确实来自结构性缺陷，可以扩大修改范围，但必须先用证据解释扩大范围的必要性。

## 8. 验证方式不是一刀切

### Dart 业务逻辑或普通 UI

优先使用热重载或热重启，再执行对应操作。大写 `R` 必须在显示 Flutter 调试按键提示的 `flutter run` 或 `flutter attach` 窗口中按，不能在 `debug_log.bat` 日志窗口中按。

### 页面初始化、WebView 或注入 JS

热重启后，可能还需要：

- 刷新当前网页；
- 重新进入页面；
- 重建 WebView；
- 清除仅与本轮测试相关的页面状态。

具体采用哪一种，由修改实际生效路径决定。

### 原生 Android、Kotlin、Manifest、Gradle 或插件原生代码

重新构建并使用覆盖安装：

```text
adb install -r
```

需要降级安装调试包时，可按实际情况使用项目脚本中的兼容参数。禁止通过会先卸载应用的方式安装，以免清空用户数据。

### 数据结构、持久化或迁移

必须验证：

- 旧数据能否正常读取；
- 新数据能否正确写入；
- 失败时是否保持数据完整；
- 是否存在重复、误删或不可逆转换。

### 调试脚本

可参考：

```text
tool/run_debug_phone.bat
```

也可使用本机已经配置的对应桌面快捷方式。运行前要确认设备、当前调试会话和脚本副作用。该脚本可能绑定具体设备，并会停止旧的 Flutter/Dart 调试进程，因此不能无条件执行。

每次修改后，由助手明确指定唯一、足够的验证方式，例如：

```text
在 Flutter 调试窗口按大写 R
```

或：

```text
按大写 R → 刷新网页 → 重新执行刚才的操作
```

或：

```text
运行桌面重启脚本 → 等 App 启动
→ 重新打开 debug_log.bat → 再执行刚才的操作
```

用户不需要自行猜测应采用哪一种。

## 9. 工程安全底线

1. 优先覆盖安装，禁止无意卸载或清空应用数据。
2. 删除、迁移、覆盖用户数据前必须得到明确授权。
3. 下载、查重、删除、迁移等操作采用 **fail-closed**：
   - 不确定目标时不执行；
   - 失败时明确报告；
   - 不制造“看似成功”的错误副作用。
4. 不把敏感信息写入日志、代码或交付内容。
5. 不修改当前目标以外的功能，除非它是修复所必需的依赖。
6. 不以“构建成功”替代功能验证，也不以“一次成功”掩盖明显的回归风险。

## 10. 验证强度与风险匹配

### 低风险修改

例如文字、局部样式、独立条件判断：

- 定向静态检查；
- 最小功能复测。

### 中风险修改

例如交互流程、网页注入、下载解析、状态管理：

- 定向静态检查；
- 相关测试或构建；
- 真实操作复测；
- 检查一个邻近场景。

### 高风险修改

例如数据迁移、删除逻辑、权限、安装、媒体库写入、跨模块重构：

- 修改前确认数据与回退方案；
- 完整相关测试和构建；
- 正常路径、失败路径和边界路径验证；
- 明确说明仍未覆盖的风险。

验证失败时，不通过绕过检查或删除测试来制造“通过”。

## 11. 完成标准

一个目标只有同时满足以下条件才视为完成：

1. 当前行为达到用户明确的预期。
2. 问题对象的必要结构、生命周期、真实入口和关键不变量已经清楚。
3. 根因或实现依据已经由证据支持，不是偶然碰巧成功。
4. 相关静态检查、测试或构建已通过；无法执行的项目已说明原因。
5. 没有发现明显错误副作用。
6. 必要的邻近场景和不可破坏的已有能力已验证。
7. 临时诊断代码已经清理，或说明了保留理由。
8. 用户需要执行的复测步骤足够短且明确。

不能验证的内容应标为“未验证”，不能写成已经完成。

---

## 12. 助手的交付格式

每轮完成修改后，使用以下简洁结构：

```text
结论：根因是什么，证据是什么。

改动：修改了哪些文件和哪条因果链。

验证：已经完成哪些 analyze / test / build / 运行检查。

复测：用户只需执行的最少步骤。

风险：仅在确有未验证项或剩余风险时列出。
```

如果本轮只完成诊断而未获授权修改，应明确写出“尚未改码”。

## 13. 何时探索，何时直接处理

适合扩大探索范围：

- 完全陌生的模块；
- 多个互相独立的失败同时出现；
- 当前代码没有明显入口；
- 问题跨越 Dart、WebView、原生层和外部服务；
- 现有证据互相矛盾。

适合直接进入本地闭环：

- 用户能稳定复现；
- 已有唯一日志前缀或异常栈；
- 调用链入口清晰；
- 错误由编译器、测试或代码直接证明。

探索的目的必须是回答具体问题，而不是制造大量无结论的扫描结果。

---

## 14. 多目标推进方式

不要把“整个应用变完美”作为单次任务。按用户当前优先级逐项闭环：

1. 明确当前最重要的一个结果。
2. 完成该结果的证据、修改和验证。
3. 确认没有阻塞性副作用。
4. 再进入下一个目标。

复杂目标可以拆为：

- 核心结果正确；
- 失败行为安全且清楚；
- 数据或媒体质量达标；
- 自动化流程稳定；
- 邻近场景无回归；
- 保留必要的长期可观测性。

独立且不会互相干扰的只读调查或验证可以并行；可能同时修改同一调用链的工作不并行。

## 15. 实战执行闭环

后续实际调试默认按以下顺序执行：

```text
启动 App
→ 打开 debug_log.bat
→ 用户操作测试
→ 发现问题后保留现场并告诉助手
→ 助手读取本轮日志和相应代码
→ 判断证据是否足够
   ├─ 足够：直接修改证据指向的问题
   └─ 不足：加入足以区分原因的最小调试日志
→ 助手指定 R / 页面刷新 / 重新进入 / 桌面重启等验证方式
→ 若 App PID 已变化，重新打开 debug_log.bat
→ 用户复测完全相同的问题点位
→ 判断结果
   ├─ 成功：检查明显副作用和必要的邻近场景
   └─ 失败：读取新日志和当前代码，进入下一轮短闭环
→ 直到问题可复现地解决并达到完成标准
```

执行时遵守以下细则：

1. 发现问题后优先保留现场，先记录日志和现象，再按助手指示重启。
2. 用户不需要自行筛选或复制长日志，只需说明本轮操作已经完成。
3. 助手优先读取 `debug_logs/debug_log_latest.log`，并结合时间戳文件和当前代码建立因果链。
4. 日志要“足以区分原因”，而不是无边界增加数量。
5. 每轮只要求用户执行最少且明确的验证动作。
6. 一次成功后仍需检查与本次修改直接相关的错误副作用；确认完成后再进入下一个目标。

## 17. 最终准则

高效协作不等于少做验证，也不等于堆积日志和方案。真正高效的是：

```text
少猜测
+ 先理解对象
+ 证据足够
+ 改动最小
+ 验证匹配风险
+ 用户操作最少
+ 结果可复现、可解释、可回退
```

后续遇到具体问题时，以本文件作为默认协作约定；若用户在当前对话中提出更具体的要求，则以当前明确要求为准。
